## Project Overview

Open water swimming conditions app (shallweswim.today). Aggregates tide, current, and temperature data from NOAA CO-OPS, NOAA NDBC, and USGS NWIS APIs for multiple locations.


## Critical Rules

1. **Use uv for everything** - Never use pip, poetry, or bare python. Always `uv run <command>`.
2. **Run commands from repo root** - Don't cd into subdirectories.
3. **Run pre-commit after major changes** - Catches formatting, linting, and type errors.
4. **Run integration tests before finishing major changes** - They hit live external APIs, so use unit tests during development, but run integration tests (`uv run pytest --run-integration -v`) to validate before considering the work done.
5. **Follow ARCHITECTURE.md strictly** - See [ARCHITECTURE.md](ARCHITECTURE.md) for architecture and coding standards.
6. **Never modify station configurations** - Do not change NOAA/USGS station IDs or data sources without explicit user approval. Configuration changes are out of scope.
7. **No AI attribution in commits** - Do not include "Co-Authored-By", "Generated by", or similar AI tool author mentions in commit messages or code comments.
8. **Never git commit without explicit user approval** - Stop and present the changes to the user. Only run `git commit` when the user explicitly says "commit". Never include `git commit` in plans or run it proactively.
9. **Documentation is current state only** - Every document describes the system as it is; history is `git log`. Propose a change by editing the owning document to the intended state with a one-line pending marker, and remove the marker in the commit that lands the code. An effort that needs sequencing across several commits gets one file in `design/` for its plan, rationale, and status, never for contracts, and that file is deleted in the commit that lands its last slice. Each subject has one owning document (see ARCHITECTURE.md "Documentation"); update it and the docstrings in the same commit as the code.
10. **Keep all Playwright versions aligned** - Python `playwright` in `pyproject.toml`, frontend `@playwright/test` in `frontend/package.json`, and the `mcr.microsoft.com/playwright` image in `.github/workflows/frontend.yml` must use the same version. The Python and frontend packages share the same browser cache. Do not run browser installation as a routine checklist step. If `--run-browser` tests or `corepack pnpm@10.18.3 --dir frontend test:e2e` report missing Chromium, run `uv run playwright install chromium` and retry. This is project-local test environment preparation; do not run `playwright install-deps` unless system packages are explicitly needed and approved.
11. **Git remotes** - `origin` is the private Forgejo repository and the primary; `github` is the public GitHub repository. "Push" means `git push origin main`. Never push to `github` unless explicitly asked; publishing there is a separate decision. Continuous deployment builds from GitHub `main`, so unpublished work deploys only through `build_and_deploy.sh`.
12. **Never modify global system state** - Do not run commands that modify state outside this repository (e.g., `gcloud auth activate-service-account`, `gcloud config set`, `npm install -g`, etc.). All credentials and configuration should come from `.env` or `.envrc` files via environment variables. Use `GOOGLE_APPLICATION_CREDENTIALS` and `CLOUDSDK_CORE_PROJECT` env vars for gcloud, not `gcloud auth` commands.

## Architecture Quick Reference

```text

Publishing job: updater → Feed → ApiClient → External Service → published generation
```


## Error Handling Philosophy

Two error types for data availability:

| Error | Layer | When | Result |
|-------|-------|------|--------|
| `StationUnavailableError` | Backend (`clients/`) | NOAA/USGS returns no data | Schedules retry, swallowed |
| `DataUnavailableError` | Core (`core/queries.py`) | Request for unavailable data | HTTP 503 |

- **Internal bugs (our code)**: Fail fast, log ERROR, let it crash - developers need to notice and fix
- **External API failures (NOAA, USGS)**: Retry transient network/protocol failures and HTTP `429`/`5xx`; log WARNING for station unavailability, ERROR for unexpected - continue with scheduled retry
- **Feed scheduling**: All fetch attempts (success or failure) schedule next attempt at expiration interval - prevents runaway retries
- **Data queries**: `get_feed_data()` raises `DataUnavailableError` (not assert) - API catches and returns 503
- Never silently swallow errors - always log at appropriate level (WARNING for expected, ERROR for unexpected)

## Before Implementing

- Check existing patterns in similar code before writing new code
- New locations: start with `NEW_LOCATION.md`. If existing source clients are enough, keep the change config-focused in `config/locations.py`; do not edit route/web/feed code or add tests that duplicate ordinary config values. If a new upstream client/feed is needed, follow `NEW_DATA_FEED.md` first.
- CPU-bound work (plotting): Must use process pool, not async
